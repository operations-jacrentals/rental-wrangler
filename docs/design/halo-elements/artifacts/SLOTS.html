Wired to the rail: --x/--y placement, --h/--ft/--fb the bar row's own geometry, and --bw/--bh the root's recorded bounding box. Turn a knob, hit copy CSS, and the printed rule lands on .halo-slots — swap in the variant you're actually editing (e.g. .halo-slots.is-c2a) before it goes into parts/slots.css.

--ft/--fb aren't just fade lengths — .b::before's pale specular cap sits at top: calc(var(--ft) - 2px), so nudging --ft carries the highlight along with it, by design.

--bw/--bh won't visibly move anything, on any of the three specimens. The root has no background and no overflow, so its own box never clips is-c2a/is-c2c — turning these two is pure bookkeeping there. On is-c2b the clip-path is real, but its insets are written as calc()s against --iy/--h/--clip-r specifically so — per the part's own comment — "the clip stays glued to the bar row" even as --bw/--bh change; the math cancels out on purpose. Moving these sliders only updates the number the part's header calls "the NOMINAL measured painted bounding box for THAT instance" — useful to keep honest if you've also moved --h, not something you'll see move on stage.

Not on the rail. Each bar's own left offset, the internal --iy row offset, and --clip-r (the fixed cut position is-c2b's clip-path is really anchored to) are baked source measurements, not free knobs — the part's own header says so outright. Per-bar colour (.r red / .y yellow) is a class on each bar's own span, not a custom property, so it isn't wireable to a slider either — it's markup, hand-edit it if a bar needs to change teams.

All three stages carry real air past the nominal box: skewX(18deg) throws each bar's top edge left and bottom edge right by roughly ±8 to ±10px depending on bar height, and filter: blur(1.4px) adds another ~2.5px on every side. Push --h or --y far enough and the stage's own edge may start cropping a bar — that's the stage running out of room, not a defect in the part.
